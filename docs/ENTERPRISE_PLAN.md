# แผนพัฒนาใช้งานภายในองค์กร

## ขอบเขตและสมมติฐาน

ใช้งานในวิทยาลัยเดียว มีทีมแนะแนว 2 สาย ใช้ข้อมูลโรงเรียนและรายชื่อผู้รับผิดชอบร่วมกัน
คงโมดูลโรงเรียน ยื่นหนังสือ นัดหมาย ปฏิทิน ออกปฏิบัติงาน คลังภาพ และรายงานเดิม
ผู้บริหารและผู้สังเกตการณ์อ่านข้อมูล เจ้าหน้าที่ทำงานประจำ ผู้ดูแลจัดการสิทธิ์
หากต้องจำกัดข้อมูลรายทีม/หลายวิทยาลัย ต้องออกแบบ query และกฎใหม่ก่อนใช้จริง

## ระยะ 1 — ฐานสิทธิ์และความถูกต้อง (พัฒนาในครั้งนี้)

- บัญชีจริงและโปรไฟล์อนุมัติตาม UID; ไม่มีการสวมบัญชีทดสอบ
- กฎอ่าน/เขียนตามบทบาท และป้องกันแก้สิทธิ์ตนเอง
- UID provisioning ผ่านหน้าตั้งค่า และติดตามการระงับสิทธิ์
- ประวัติการทำงานสำหรับผู้ดูแล; สถานะโหลดข้อมูลผิดพลาด; แก้ฟิลด์วันที่
- ไม่แจ้งว่าส่งอีเมล/อัปโหลดสำเร็จเมื่อระบบจริงยังไม่สำเร็จ
- คู่มือตั้งค่าบัญชีและชุดทดสอบ unit/Firestore rules

เกณฑ์รับ: lint/build/unit tests ผ่าน และ rules integration tests ผ่านใน Emulator
สถานะ: โค้ดเสร็จ ต้องทดสอบ rules และ UAT กับ Firebase ที่องค์กรจัดเตรียมก่อนเปิดใช้งาน

## ระยะ 2 — กระบวนงานร่วมกัน

1. ย้ายการจองนัดหมายไป Cloud Function/transaction ใช้ slot lock ต่อทีม เจ้าหน้าที่ และรถ ป้องกันจองซ้อนพร้อมกัน
2. ออกแบบสถานะ ร่าง → ขออนุมัติ → อนุมัติ/ส่งกลับ → ดำเนินงาน → ปิดงาน พร้อมผู้อนุมัติ เหตุผล และเวลา
3. บันทึกการยื่นหนังสือ/ออกแนะแนวและสถานะโรงเรียนใน atomic batch หรือ server transaction
4. เพิ่มตัวกรองปีการศึกษา สายงาน สถานะ และผู้รับผิดชอบ โดยให้ตัวกรองใช้ร่วมกับรายงาน
5. ตรวจ required fields, จำนวนผู้เรียน, เวลาเริ่ม/สิ้นสุด และความสัมพันธ์โรงเรียนบน server

เกณฑ์รับ: ทดสอบ 2 บัญชีจองพร้อมกันได้ผู้ชนะเพียงรายเดียว; อนุมัติย้อนหลังตรวจสอบได้; ข้อมูลโรงเรียนและกิจกรรมไม่ค้างคนละสถานะเมื่อเขียนล้มเหลว

## ระยะ 3 — โครงสร้างพื้นฐานองค์กร

1. SSO ขององค์กร/MFA, invitation ผ่าน backend, อายุ session และขั้นตอนพนักงานพ้นสภาพ
2. จัด Storage rules ตามสมาชิกและบทบาท ตรวจชนิด/ขนาดไฟล์; ทบทวนลิงก์รูปที่แชร์ได้
3. Server audit แบบ append-only ทุก mutation มี actor UID, before/after, request ID และ server timestamp
4. ระบบอีเมลผ่าน scheduler + queue + provider แยก queued/delivered/failed และป้องกันการส่งซ้ำ
5. สำรอง/กู้คืน, แยก staging/production, error monitoring, นโยบายเก็บข้อมูลและผู้รับผิดชอบ
6. ปรับ dependencies, lazy loading, pagination และ query indexes ตามปริมาณข้อมูลจริง

เกณฑ์รับ: ทดสอบเพิกถอนสิทธิ์, กู้คืนข้อมูล, งานแจ้งเตือนเมื่อปิด browser และการห้ามเข้าถึงไฟล์โดยผู้ไม่มีสิทธิ์

## ระยะ 4 — ทดลองและเปิดใช้

- ทดลองทีมละกลุ่ม ตรวจ workflow ตั้งแต่เพิ่มโรงเรียนจนส่งออกรายงาน
- ทดสอบมือถือ คีย์บอร์ด เครือข่ายขาดช่วง ข้อมูลจำนวนมาก และความผิดพลาดจาก server
- ย้ายข้อมูลจริงหลังสำรองและตรวจ mapping UID/โรงเรียน/นัดหมาย
- อบรมผู้ดูแลและเจ้าหน้าที่ พร้อมคู่มือกู้คืนและช่องทางรับปัญหา
- เปิดใช้เมื่อรายการรับงานด้านความปลอดภัยและความถูกต้องผ่านทั้งหมด

## ข้อจำกัดที่ต้องตกลงกับองค์กร

ยืนยันผู้อนุมัติ, ผู้ที่เห็นข้อมูลติดต่อ, ต้องแยกข้อมูลตามทีมหรือไม่, ผู้ให้บริการ SSO/อีเมล, ปริมาณรูปต่อปี, ระยะเวลาเก็บข้อมูล และงบ Firebase ก่อนระยะ 2–3
